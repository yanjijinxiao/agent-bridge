# 渠道账号的首次对话与群成员绑定

## 功能和配置

Connector 的设备配置文件（启动时通过 `--config` 指定）用顶层字段 `onUnbound` 决定何时自动创建。机器人账号保存群绑定范围和默认 Connector。新设备省略该字段时默认手动绑定。一对一私聊仍使用原绑定。启用群成员模式后，同一成员在不同群有不同的绑定。同群不同成员独立提交、续聊、解绑和收取结果。群内消息对全群可见。

| Connector 配置 `onUnbound` | 从未绑定时发普通消息 | 主动或闲置解绑后发普通消息 |
| --- | --- | --- |
| 提示绑定会话（`manual`） | 提示选择会话 | 提示选择会话 |
| 仅首次自动新建（`create`） | 创建默认会话 | 提示选择会话 |
| 每次未绑定时自动新建（`create-when-unbound`） | 创建默认会话 | 在配置的 Connector 创建全新会话 |

在 IM 中发送 `/leave` 或 `/unbind`，会同时解除当前绑定，并重置本人在当前聊天的 Connector 选择。重复发送也能清除旧版本留下的设备偏好。下一条普通消息按账号当时的默认设备及其策略处理。主动另选设备后使用新选择。群内其他成员和本人在其他聊天的设备偏好独立保存。Web 管理员按绑定解绑及闲置到期只处理会话绑定。

三种设置下，已有绑定都继续使用原会话。更改设置和解绑本身均不创建会话。新会话由之后收到的首条普通消息触发，同一绑定范围内同时到达的消息共用一次创建。此前已绑定到旧会话的待转发输入保留原目标。已注册命令与卡片操作走原处理器，未注册斜杠文本沿用普通输入规则。

## 模块和函数契约

- 入站在保存转发记录前冻结会话范围。账号状态文件已隔离账号。群成员绑定由平台确认的真实群和发送人共同确定。审批、队列、任务卡和恢复使用同一绑定标识。对外投递、群准入与 Connector 配对使用真实群标识。
- 首次普通消息经过准入和角色校验后，在指定 Connector 独立目录创建原生 thread。创建和提交使用独立来源回执。并发首条输入共享同一创建身份，创建结果及绑定一次落盘。提交回执不明沿用原生核对。没有确认的原生创建结果不能被推断为成功。
- 判断首条普通消息时，正文、直接附件和渠道提供的引用都算输入。只有引用时也使用本次发送者的身份进行准入和群成员绑定；引用里的作者和命令仅作为资料。空正文且没有附件或引用时不创建会话。
- `BridgeService.firstContactRoute` 为私聊与群成员选择本人在当前聊天选定的 Connector；没有选择时使用账号指定的设备。全群共用绑定时仅使用群所属账号指定的设备。`allowsUnboundSession` 根据目标设备策略及解绑标记决定是否允许自动创建。入站登记、原生创建前后、专用设备创建授权及状态提示使用同一规则。直到新绑定落盘才清除解绑标记。再次解绑会作废先前的创建编号。旧群绑定与个人绑定分开；授权或配置改动期间在途的输入不能改投。
- 开启自动创建本身不发放设备目录、浏览器或项目权限。设备不可用时保留原目标。查询、管理命令与卡片回调均不能触发首次创建。

## 四层验收

1. 架构：沿真实钉钉入站、转发日志、Connector、App Server、卡片和钉钉投递走通；核对入站身份与收件地址。
2. 模块：同人连续首条、同群两人、跨群、私聊、撤权、设备离线、原生回执未知、显式绑定、解绑、旧记录和恢复。
3. 文件与函数：核对创建幂等身份、绑定落盘、审批与停止的目标、队列排序和输出目标，保留精确测试断言。
4. 静态配置：校验账号配置读写、默认值、管理页、文档及既有设置的兼容性。隔离渠道端到端与真实客户端投递分别留证。

## 管理员设置

钉钉账号的「渠道设置」提供「群聊会话归属」和「默认执行设备」，设备列表显示最近一次上报的策略。设备管理员编辑 Connector 配置后重启该 Connector 即可更新策略。默认设备使用部署中的稳定主机标识。私聊沿用渠道确认的私聊地址。切回全群共用时，后续输入回到群绑定；旧任务的回执、进度及带编号的问题仍归原投递位置。

`PeerRegistry` 只在设备认证、登记完成后按节点和 profile 保存最后一次上报的策略。Gateway 冷启动时可识别离线设备，重连后按最新策略重新核对。在途创建同时核对原设备、持久化的选择代次与创建回执。设备清除字段后移除缓存。旧账号的 `onUnbound: create` 仅对其原默认设备兼容，且仅在该设备未声明策略时使用。显式 `manual` 始终优先。

普通 Connector 继续使用已有授权。管理员若要给成员一个只供首次对话的受管 Codex 执行入口，可在 Gateway 已配置的 managed route 上设置 `firstContactOnly: true`，再在渠道设置里选它。该设备不进入用户的设备目录，也不因自动建会话而授予 Web IDE。首次创建需要当前账号、来源及持久化创建编号同时匹配。后续聊天 RPC 仅放行列明的原生方法和属于该成员或原群绑定的 thread。专用路由的授权限制在 Gateway 一侧生效，Connector 继续使用原有的双端托管凭据和标准 App Server 接口。独立工作目录隔离项目文件的默认位置。部署主机和 Codex 的沙箱策略决定实际操作系统文件权限。

## 卡片顶部与恢复

状态、沙漏和耗时沿用原顺序，在同一行末尾追加「默认会话/绑定会话＋会话名称 · 机器」。自动创建且仍叫「默认会话」时显示原生会话 ID 的短尾号；机器取当前执行主机在 Connector 中的标签。首次建卡保存该行的归属，恢复、阶段换卡、分页最终结果及合并参与者提醒时沿用。已开始投递的旧版结果沿用其原分页。阶段成果、项目符号、命令复制框、原生加载提示及 Web IDE 页脚仍由各自的渲染函数负责。

平台回报卡片已创建、已送达时，回执携带真实群号。投递适配器先校验群号，再把回执交给发起该次投递的成员绑定。恢复卡片时先核对持久记录里的成员和卡片编号，再传回平台所需的群号。即使两个人在同一群，也不能拿另一人的回执续写自己的卡。

后台观察按每条个人订阅的账号、群和发送人执行原生读取。两条订阅即使指向同一原生 thread，也只在读取权限相同的前提下共享快照。

## 验证入口

- `test/member-sessions.test.ts` 从账号 monitor 的 claim 和 receive 进入真实转发日志、BridgeService、WebSocket Connector 和持久化会话。覆盖双成员并发、来源重复、跨群与私聊、重启续聊、成员互答与审批、解绑、专用设备目录与跨成员权限。设置 `CODEX_NATIVE_QUEUE_TEST_BIN` 后会额外启动测试独占的原生 App Server，对照解绑前后的原生历史，核实首条与后续消息均进入新会话。模型供应方和 IM 传输为本机测试替身。
- `test/connector-first-contact.test.ts` 与 `test/connector-selection.test.ts` 覆盖带旧 Connector 的对话解绑、同群和跨群的个人设备选择、旧卡片、重启、目录查询和默认设备热更新。另核对同名设备的独立策略、两个机器人分别授权、切换与续聊、群共用路由以及 Gateway 冷启动时的策略读取。
- `test/command-status-routing.test.ts` 检查闲置解绑后的状态提示、命令与普通消息的区别和未准入发送者。`test/settings-draft.test.ts` 核对管理页的默认设备和设备策略回显。
- `test/compact-progress-design.test.ts` 比对改动前后正文、页脚和合并提醒；`test/dingtalk-progress-layout.test.ts` 检查 HTTPS 和 SDK 实际发出的组件内容、顺序、复制框数量、链接、终态及旧检查点；`test/peer-native-compat.test.ts` 包含 Connector 尚未上线的历史绑定。
- 钉钉回调级用例调用真实适配器，输入两位成员的群消息，经过 Gateway、Connector 和原生 Codex 后，核对两张进行中卡的状态、两个不同的会话短号、最终正文、收件群和各自的 @ 名单。[四层检查记录](../audits/2026-11-25-member-sessions.md)
