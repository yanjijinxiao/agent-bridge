# Gateway 功能与架构契约（复核中）

本文件从本会话 3229 条可恢复的公开文字记录提炼，和机器清单 gateway-requirements.json 对应。它描述应有行为，不代表所有条目已经实现或验证。逐行阅读及验证进度见本轮 audit 目录。历史引用97个不同图片路径中，92张仍存在且已逐张打开，5张早期临时图丢失；不能把旧图当作当前客户端验收。

## 权威和职责边界

Codex 原生服务持有线程、执行、原生队列和原生工具授权；Gateway 持有 IM 来源、绑定、交接及投递回执；渠道确认平台业务接收；客户端是否展示需要单独验证。Web IDE 的浏览器授权由 Gateway 持有，不能拿 Codex 的沙箱或群准入替代。

一套 App Server 接口覆盖本机与远端、桌面与纯 CLI。差异仅在主机连接和服务部署。业务层不按桌面/headless 分叉，连接错误不授权切换执行器。

## 必须独立保留的状态

| 对象 | 状态依据 | 不允许的推断 |
| --- | --- | --- |
| 输入 | 来源持久化、原生接收和精确消息/轮次 ID | RPC 超时等于未执行，可重发 |
| 任务 | 原生精确线程/轮次及权威运行态 | 进展静默、卡片失败等于任务停止 |
| 投递 | 卡片创建、业务发送、更新、分页各自回执 | HTTP 200 或 SDK 返回就等于用户看见 |
| 绑定 | 账号、聊天、host/thread 和变更代次 | 同 cwd 等于同项目或跨群可转发 |
| 交互 | 原请求 ID、原选项、原操作者和确认事件 | 提交答案/审批就等于已生效 |
| IDE | 原生项目归属、所有根目录、原浏览器证明及持久授权 | 本机可连就等于手机可达 |

## 已取代的旧决定

- 普通运行中消息以最新 steer 默认值为准；显式会话策略保留。早期默认 ask/queue 不再作为默认。
- 显式 queue 使用原生持久队列，Gateway 只保存来源及回执；旧的本地 prompt 队列不是当前实现目标。
- Codex exec/私有 IPC 的生产回退和桌面/headless 业务分支已取消；兼容类型不能恢复为执行入口。
- AI Card 投递不确定时自动另发文字的方案已被用户取消。渠道本身只支持文字时仍使用其原生文字流程。
- 复制控件只提供完整必要回复或跨页面转移值；展示路径、枚举和说明不因形式相似而获得复制按钮。
- IDE 授权采用原浏览器证明和一次明确 IM 确认，复用个人准入，90 天持久化；旧额外密码/两次确认/15 天方案不再适用。
- 本机入口按本机实际网卡/固定内网路由；远端入口按项目所在主机配置。旧统一中转或变化 VPN 地址不能覆盖后续要求。
- 重启只保护 Gateway 未完成交接。已接收的独立原生执行不阻止重启；用户取消了长期后台等待切换机制。

实际入口、状态写入者和待核对架构边界见 gateway-implementation-map.md。

## 模块契约与场景

### native · Codex原生协议与连接

原生服务保存执行、线程、队列、工具授权；Gateway只归一化协议，不发明终态或新执行器。

**NATIVE-01 · 一套完整原生接口**

桌面与 CLI 只区分部署及传输；所有生产操作使用同一 App Server 适配器，不自动换执行器，不用禁用功能代替适配。

历史来源记录：3179, 3180, 3183, 3186。实施/验证状态以 JSON 清单为准。

- NATIVE-01.1：无桌面注册表也可新建、继续、跟随、交互、排队、目标和历史
- NATIVE-01.2：断连后不启动第二执行器、不转 exec/私有 IPC
- NATIVE-01.3：旧 auto/exec 配置迁移后只实例化原生适配器
- NATIVE-01.4：转发子进程关闭输入后，异步 EPIPE 结束原连接并返回通信失败，不以未处理 error 事件杀死 Gateway。
- NATIVE-01.5：进度及不支持审批/MCP/提问通知的观察者同步抛错或异步拒绝，不使 Gateway 崩溃、不切断原连接、不代答原请求。

**NATIVE-02 · 同一原生核心与权限继承**

按主机固定核心；继续现有线程继承原生 sandbox、reviewer、权限，不从回调存在与否推断。

历史来源记录：3151, 3182, 3186, 3217。实施/验证状态以 JSON 清单为准。

- NATIVE-02.1：两个客户端继续同一线程并看到同一活动轮次
- NATIVE-02.2：有无审批回调均不重置已有工作区可写和自动审核
- NATIVE-02.3：Gateway 断连重连不抢锁、不改变 core/线程/输入次数
- NATIVE-02.4：续聊拒绝其他、缺失或空的线程 ID，预检拒绝其他线程快照；原生身份校验失败前不写标题、项目或输入，不产生接收事件。

**NATIVE-03 · 全部控制按主机路由**

模型、额度、运行态、目录、目标、队列、审批和执行同属选定 host 的原生服务；本地默认不覆盖远程上下文。

历史来源记录：143, 801, 2770, 3173。实施/验证状态以 JSON 清单为准。

- NATIVE-03.1：本地远程同 threadId 不串状态、模型和额度
- NATIVE-03.2：远程目录/模型读取失败不改为本机结果
- NATIVE-03.3：等待期间换绑后原查询不改新会话设置
- NATIVE-03.4：模型/强度/额度查询经 IM、管理层和公开 facade 保留远程 host/cwd/thread，本机默认仍正确，远程失败不换本机账号
- NATIVE-03.5：模型、强度及额度只读查询等待期间换绑或撤销个人准入，旧账号/模型结果不回送

**NATIVE-04 · 轻读与历史隔离**

同核心的元数据、诊断及大历史使用隔离读连接；只读超时不关闭执行连接，不提交任务。

历史来源记录：2571, 3091, 3092。实施/验证状态以 JSON 清单为准。

- NATIVE-04.1：挂起历史查询时状态和新输入仍能响应
- NATIVE-04.2：只读重建始终附着原核心，不创建另一个核心
- NATIVE-04.3：显式 stdio 共享原连接且准确报告随 Gateway 退出的生命周期限制

**NATIVE-05 · 线程和轮次状态正交**

持久化、runtime、turn 与提交/投递状态独立；终态须来自原生真实执行者或明确结束事件。

历史来源记录：415, 418, 420, 2690。实施/验证状态以 JSON 清单为准。

- NATIVE-05.1：archived、missing、notLoaded、unknown、systemError 分别处理
- NATIVE-05.2：旁路历史 interrupted 不结束原生仍 active 的卡
- NATIVE-05.3：晚到旧 turn 完成不清新 turn 处理器
- NATIVE-05.4：原生未知/新增运行态不能由历史尾轮 completed/failed/interrupted/inProgress 推断为 idle/active；历史事实单独保留。四个线协议反例原版均失败。

**NATIVE-06 · 长任务不因静默超时**

有界 RPC 等待不等于任务寿命；确认接收后任务可长期无输出，通信异常仅改变观察状态。

历史来源记录：144, 145, 148, 150。实施/验证状态以 JSON 清单为准。

- NATIVE-06.1：接收后静默超过普通 RPC 预算仍保持任务
- NATIVE-06.2：读取超时不发 interrupt、不伪造 failed
- NATIVE-06.3：通信恢复沿原 turn 继续，不重放输入

### inbound · 消息接收与交接

平台提供事件身份与内容，Gateway持久接收并绑定来源；原生回执决定是否已接收。

**IN-01 · 普通消息透明转发**

仅显式斜杠命令及可信原生交互走控制分发；普通自然语言、附件与引用完整交给选定会话。

历史来源记录：2697, 2699, 2700, 2711。实施/验证状态以 JSON 清单为准。

- IN-01.1：包含切项目、review、建群等自然语言不触发菜单
- IN-01.2：引用里的 /stop 或 /approve 不是新命令
- IN-01.3：四种渠道共用分发语义，任务/知识扩展仅在明确模式内生效
- IN-01.7：钉钉有效消息先经同步持久化 claim，再回 provider ack；已保存重复仍 ack，磁盘失败不 ack、不派发；停止后的旧 monitor 不能以 false 冒充重复。

**IN-02 · 可靠接收与持久交接**

先保存完整正文、附件、来源和目标再交接；明确未提交可恢复，已接收和回执未知不重发。

历史来源记录：3019, 3020, 3022, 3036。实施/验证状态以 JSON 清单为准。

- IN-02.1：提交前崩溃后平台重投或恢复只执行一次
- IN-02.2：原生接收后落盘前断连保留未知，不重发
- IN-02.3：写盘失败不确认成功、不向 Codex 写入
- IN-02.6：显式 steer/queue 的附件与状态准备在实际提交前完成来源复核；零写入拒绝不能记成提交未知，已经发生的原生/本地副作用仍保留去重。具体模块设计见 modules/inbound-forwarding.md。
- IN-02.4：飞书普通文本、未知格式、卡片点击和菜单的持久化 claim 失败后，报告一次错误、零派发并拒绝到 SDK；已保存重复仍正常返回。本机已读 SDK 确认 handler rejection 对应非成功源响应，未冒充真实供应商重投验收。
- IN-02.5：显式消息合并区收集中的文字跨重启恢复、done 准备失败保留、未知提交跨重启持有且不重发、原生接受后即使任务失败也不复用旧内容。前三项修改前失败，接受后失败为正常对照。 同一原生线程切换任务板视图仍保留 collecting 内容；这是本轮新增范围校验过严的回归，已补正常路径用例，未作为旧版缺陷。

**IN-03 · 未知前序不永久阻塞**

真正进行中的交接顺序受保护；前序已结束但回执未知不永久挡住后续独立输入。

历史来源记录：3197, 3198, 3205。实施/验证状态以 JSON 清单为准。

- IN-03.1：未知前序后新消息仍可转发
- IN-03.2：进程重启保留原未知记录且不重放
- IN-03.3：上一条慢结果投递不把下一条误判为提交中

**IN-04 · 群命令归一化**

按可信机器人身份处理 @ 前缀，别名先归一化再角色检查；保留中文、多行和引用边界。

历史来源记录：1043, 1051, 2737, 2741。实施/验证状态以 JSON 清单为准。

- IN-04.1：紧邻 @、换行、/queue紧接中文都进正确命令
- IN-04.2：普通正文中的人名和 @ 不任意删除
- IN-04.3：重复平台事件只认领一次且失败可观测

**IN-05 · 入站附件和引用**

渠道负责提取真实正文及下载凭据，授权后有界下载；引用是资料，不能假装读取仅有文件名的附件。

历史来源记录：1347, 1354, 1357, 1365。实施/验证状态以 JSON 清单为准。

- IN-05.1：纯图、混排、普通文件及引用文件保留原语义
- IN-05.2：只有文件名或引用ID时明确缺内容
- IN-05.3：下载超限、超时、存储失败不静默丢消息
- IN-05.5：允许目录按真实现有祖先限界：现有越界软链接、未创建子路径、有效配置别名、根内未来路径、同名前缀兄弟和悬空链接逐一断言。修改前首个越界反例失败；不声称六例修改前均失败，也不声称消除可变父目录所有 TOCTOU。

**IN-06 · 跨主机资源**

本机附件显式转存原会话主机；远程结果不能拿本机同路径文件冒充。

历史来源记录：801, 1361, 2803。实施/验证状态以 JSON 清单为准。

- IN-06.1：远程 Codex 收到远端可读附件路径
- IN-06.2：转存中途换绑/撤权后不提交
- IN-06.3：远程输出未提供下载通道时明确失败，不误读本地同名文件

### state · 持久状态与账号

仓储持有内存/磁盘版本，账号运行代次约束异步资源。

**STATE-01 · 状态唯一与原子持久化**

每账号唯一状态所有者；校验和持久化成功后发布内存变更；外部变更不得被旧快照覆盖。

历史来源记录：2628, 2635, 2777, 2885。实施/验证状态以 JSON 清单为准。

- STATE-01.1：长任务完成不覆盖期间改名/解绑
- STATE-01.2：保存失败后读内存仍是旧有效状态
- STATE-01.3：损坏关键文件拒绝加载并保留原件，不当空表覆盖
- STATE-01.4：消息合并持久文件严格校验、坏文件/重复键保留；append 批次原子且按源 ID 去重，旧 binding 内容不能发向新绑定，准备可恢复而尝试提交不因收集 TTL 释放，落盘失败不污染内存。

**STATE-02 · 账号生命周期和身份**

账号停止/替换使旧异步回调失效，机器人身份取当前运行适配器；可选故障不能阻断其他资源清理。

历史来源记录：730, 2553, 2819。实施/验证状态以 JSON 清单为准。

- STATE-02.1：停止再启动只有一个状态写者和发送客户端
- STATE-02.2：旧连接回执不能写入新连接或新机器人
- STATE-02.3：单个清理失败仍尝试其余清理
- STATE-02.4：空串、点、双点账号身份不能别名到共享 runtime 或父目录；常规已安装账号规范化保持原值。

**STATE-03 · 兼容迁移与私有数据**

兼容旧目录、环境变量、动作协议、请求头，保留来源许可；真实凭据、对话和部署授权不入仓。

历史来源记录：600, 611, 589。实施/验证状态以 JSON 清单为准。

- STATE-03.1：旧安装仍使用其真实状态目录不丢账号
- STATE-03.2：迁移不扩大权限、不清空授权、不重发任务
- STATE-03.3：日志及管理响应不输出 Secret/Token/ticket

### binding · 绑定与交互目标

每条IM关系有精确host/thread和代次，主入口只是该关系的有效引用。

**BIND-01 · 未绑定与精确解绑**

允许显式无绑定；/unbind 与兼容 /leave、Web 精确解绑共用同一事务，只移除目标关系。

历史来源记录：1629, 1638。实施/验证状态以 JSON 清单为准。

- BIND-01.1：未绑定普通消息给指引，不自动建线程
- BIND-01.2：重启、模式切换不接回旧 session
- BIND-01.3：解绑一群不删除线程、不停止任务、不取消原生队列、不影响别群

**BIND-02 · 绑定是执行上下文权威**

选定 session 确定 host/thread/workspace，项目选择为投影；无项目不是无会话，不按 cwd 发明项目。

历史来源记录：2619, 2623, 2878。实施/验证状态以 JSON 清单为准。

- BIND-02.1：独立 session 残留旧项目仍可正常续聊
- BIND-02.2：换项目/模式使原输入租约失效
- BIND-02.3：查不到 native 项目只标 unknown，不清绑定或沿用其做授权
- BIND-02.4：目录相同不能替代主机/项目身份：默认本机创建不继承远程项目；同主机多个原生项目必须明确选择；显式项目有效，显式 host 用于 legacy 解析且不得覆盖所选项目 host。

**BIND-03 · 统一生命周期失效**

切换、解绑、归档、撤权、停账号统一使旧订阅/主交互/控制租约失效；已投递交互保持原来源。

历史来源记录：2432, 2434, 2437。实施/验证状态以 JSON 清单为准。

- BIND-03.1：新旧绑定不串进度/最终结果/附件
- BIND-03.2：归档暂停跟随而非伪造失败答复
- BIND-03.3：准备附件或等待后端时变化在原生写入前再拒绝
- BIND-03.4：附件下载、远端转存、原生状态检查及引用解析等待后，原会话换绑时不能把普通输入、显式 queue 或 steer 改投新线程；七条实际准备路径各有正常对照，共 14 项。旧版七项换绑均有失败证据。同一原生线程的任务板展示模式变化不视为换绑，原请求 ID 并发去重仍保留。此项不代表所有撤权/停账号分支已验收。

**BIND-04 · 主交互与来源路由**

已确认轮次来源优先，其次持久主入口，最后唯一有效绑定；进度可多跟随，交互不广播。

历史来源记录：1481, 2423, 2436, 2449。实施/验证状态以 JSON 清单为准。

- BIND-04.1：主入口切去别线程后明确失效
- BIND-04.2：冲突提示无题目敏感正文且持久去重
- BIND-04.3：恢复路由后新读原题仍有效才发，不重放旧答案

**BIND-05 · 绑定总览**

Web 与真实路由读同一份有效绑定，当前/历史分开，真实群名缺失明确待确认，提供查看/主入口/解绑。

历史来源记录：2457, 2465, 2473。实施/验证状态以 JSON 清单为准。

- BIND-05.1：渠道及项目直达筛选一致
- BIND-05.2：查看会话只导航不改绑定
- BIND-05.3：旧页面解绑版本冲突时不误删新关系

### catalog · 目录与历史

原生身份/归属是事实，置顶/排序是展示信息，cwd不是项目授权依据。

**CAT-01 · 完整普通会话目录**

全局列出可绑定未归档普通线程；不把一页/历史cwd/探活/审批子任务等同完整目录。

历史来源记录：706, 774, 781, 2664。实施/验证状态以 JSON 清单为准。

- CAT-01.1：取完原生分页后再UI分页
- CAT-01.2：普通同 READY 标题不隐藏，已确认用途标记按host/thread过滤
- CAT-01.3：远程不可用显示部分结果警告，不转本机目录
- CAT-01.4：会话/项目/模型/历史分页，以及快照/执行预检/目录补查，缺失 data、非数组、非法游标必须报告异常；分页循环拒绝重复游标。33 个异常/合法空结果场景，非分页快照允许合法后续页。

**CAT-02 · 顺序、分页与稳定选择**

置顶→原生项目顺序→其他；组内遵循原生顺序，默认10且保留5至50偏好，R快照按账号/对话/人隔离15分钟。

历史来源记录：2655, 2664, 2907, 2908。实施/验证状态以 JSON 清单为准。

- CAT-02.1：翻页/改size不重排R身份
- CAT-02.2：旧卡/过期快照不把编号解释成另一项目
- CAT-02.3：同主机同路径不同项目、跨主机同名均区分
- CAT-02.4：项目树包含没有未归档会话的原生项目；置顶不重复，离线/不完整不冒充空目录。会话与空项目分页，R 编号、详情及远端绑定保持精确，过滤不附带无关空项目。仅验证本机 Bridge/Markdown 边界，手机显示另验。

**CAT-03 · 项目身份与创建**

原生项目 ID、桌面别名、工作目录不混同；/new 当前/指定/独立，下一条消息才创建原生线程。

历史来源记录：403, 405, 702, 738, 741。实施/验证状态以 JSON 清单为准。

- CAT-03.1：无当前项目不自动选第一个
- CAT-03.2：指定远程项目保留host与完整rootPaths
- CAT-03.3：立即保存新threadId且标题不受渠道规则污染
- CAT-03.4：普通续聊继承原生项目归属：原生已移除或改绑项目时，不以旧 Gateway 项目提示覆盖；线协议假服务与真实隔离 App Server 各验证两个场景。
- CAT-03.5：无当前项目时 task/qa/mode 命令不得隐式选第一个注册项目；独立 /new 在引用准备后若账号 runtime 已退休，必须在分配目录和绑定前拒绝。四例修改前失败。

**CAT-04 · 历史与详情**

历史分页只展示公开对话和进展，详情只读；异常JSON、中文跨字节、长日志不得截断或泄内部消息。

历史来源记录：648, 717, 748, 2818。实施/验证状态以 JSON 清单为准。

- CAT-04.1：支持旧event及新response两种格式并去重
- CAT-04.2：guardian/子agent/环境/开发者指令不进入预览
- CAT-04.3：最近历史和翻页都保留正文/引用但不触发附件发送
- CAT-04.4：展示历史时，围栏、引用、嵌套代码中的附件示例、空行和图片标签保持字面内容；顶层真实附件和 Desktop envelope 元数据仍提取，不能因相同早先字节匹配错位置。

### controls · 输入和控制编排

最后外部写入前复核来源；原生队列和精确turn控制不混同。

**CTRL-01 · 普通忙时 steer**

普通运行中输入默认 steer，保留显式策略覆盖；写入匹配当前原生 turn，无未知/空闲 fallback 启动或排队。

**CTRL-02 · Codex 原生持久队列**

原生服务保存内容和顺序并消费；Gateway只存来源/回执，不维护第二执行队列或主动重复消费。

- CTRL-02.3：队列项已消失须结合回执/历史，不据此重发

**CTRL-03 · 队列恢复和取消**

恢复按精确消息/轮次对账，取消仅原生待项；终态回执不重开运行卡，读核对不长期占写锁。

- CTRL-03.3：已送达完成项迟到onAccepted不建新卡
- CTRL-03.4：只读恢复已接受的 completed/failed/interrupted 队列轮次，接收事件保留原生终态，不伪装成新运行开始

**CTRL-04 · 停止及目标身份**

stop只影响指定host/thread/turn；目标设置显式set，模型/effort按值而非变化列表序号。

历史来源记录：418, 2895, 2913。实施/验证状态以 JSON 清单为准。

- CTRL-04.1：停止空闲线程不误停另一活动线程
- CTRL-04.2：goal内容pause/clear是文本可设置
- CTRL-04.3：模型数字/default/目录重排仍选准确值
- CTRL-04.4：目标 get/set/clear 返回后按原来源核验展示；换绑、ABA、权限不足、撤权及停止后的旧结果不发送，已成功的原生修改不误报未提交，viewer 查询保持可用。详见 modules/goal-controls.md。

**CTRL-05 · 状态与帮助**

命令别名、权限、能力与帮助一致；status轻量并行有界，不被可选服务/历史/任务执行堵住。

历史来源记录：668, 1217, 2738, 2741。实施/验证状态以 JSON 清单为准。

- CTRL-05.1：约1秒查询预算返回已知与未确认项
- CTRL-05.2：帮助包含实际支持new/unbind/queue/answer/ide等
- CTRL-05.3：可选Taskboard挂起不阻塞状态或首屏

### interactions · 提问与审批

原生请求ID和可选范围是权威，交互控制器保存来源和提交/确认状态。

**INT-01 · 原生审批全范围**

按原生提供的once/session/always/reject和权限对象展示，IM/Web共用；Gateway不自行扩大或保存工具授权。

历史来源记录：2544, 2556, 2558, 2562。实施/验证状态以 JSON 清单为准。

- INT-01.1：Computer Use无once时不伪装允许一次
- INT-01.2：命令前缀、网络host、文件权限范围无丢失
- INT-01.3：不存在本地回调不自动拒绝其他客户端审批
- INT-01.4：Web 原路线在审批出现前停止或换绑、容量恢复缺少原审批路线时，未发送新审批也不合成拒绝；由原生请求保留待处理。
- INT-01.5：第二次 start 被明确拒绝时，不能清掉原轮次的审批、动态工具或问题 handler；未知 start 保留本次 owner 和 subscription，不能按忙重试。
- INT-01.6：审批通知等待进度卡更新时，原绑定被替换或账号停止，不得再新投递旧问题，也不能合成 approve/decline；返回 observation/unavailable。两项修改前均实际发送旧审批。正常审批及同三种提问路径为对照，其中提问控制器原本就正确，未重复增加 guard。
- INT-01.7：受保护管理 HTTP 与 IM 消费同一不可变审批及version，原会话/原选项核验、重复决定只处理一次；持久权限有明确范围确认，失败回执不冒充生效。仅证明本机HTTP/控制器/VM表单路径，不代表手机真实钉钉投递已验收。

**INT-02 · 真实审批与内部审核**

自动审核、工具挂起和人工待审分别表示；没有原生人工请求不画假审批卡；订阅ready以收到可信快照为准。

历史来源记录：3107, 3111, 3147, 3150。实施/验证状态以 JSON 清单为准。

- INT-02.1：首次漏快照补订阅且不把无基线增量当完整列表
- INT-02.2：空快照清理待审、非法快照不误清
- INT-02.3：断线重连原typed请求ID不变且不重发决定
- INT-02.4：原生自动审核 started/completed 仅显示其当前轮次的结果，不伪造人工问题、操作指令或泄露 reviewer/action；单有 waitingOnApproval 状态不能猜测有人工可点审批，恢复原卡后保留真实 wait-input/running 状态。

**INT-03 · 提问、表单与安全URL**

同步/异步逐题身份、自由输入、选择及类型表单适配原请求；敏感登录提供安全入口不收群内秘密。

历史来源记录：1409, 1411, 1594, 1606, 2427。实施/验证状态以 JSON 清单为准。

- INT-03.1：options为null/省略/[]均自由输入
- INT-03.2：同轮多题回答一题不取消兄弟题
- INT-03.3：MCP枚举/数值/布尔按schema回传，未知约束明确提示
- INT-03.4：原生异步问题在等待steer连接期间撤销observer、撤回/改写widget、peer已经回答、轮次结束或断连，最终原生写必须被阻止；通知微任务前撤回不得再发旧问题。使用实际AppServerCodexRunner.steer消费assertCurrent及正常无变更对照，不是旧Desktop IPC兼容测试。

**INT-04 · 答案及决定回执**

选择与原生确认独立；答案匹配host/thread/turn/question与原文证据，撤回、peer答复、晚超时不覆盖确认。

历史来源记录：1498, 1506, 1513, 1583, 3188。实施/验证状态以 JSON 清单为准。

- INT-04.1：答案只交原题一次不当普通消息
- INT-04.2：IM/Web竞争一方成功另一方失效
- INT-04.3：投递确认通知失败只重试原通知，不重交答案

**INT-05 · 异步状态不卡主线**

提问/审批卡片发送迟迟不返回，不阻塞原生答复、超时、撤销和停止；等待状态与进度正文同步。

历史来源记录：2779, 2796。实施/验证状态以 JSON 清单为准。

- INT-05.1：发送未返回时仍能处理已知QID答案
- INT-05.2：挂起投递超时不等于已自动拒绝
- INT-05.3：断连保留未知决定，不自动跳过/重发

### recovery · 恢复协调

已确认原生错误/尾轮是恢复条件，恢复与原任务失败、消息投递分离。

**REC-01 · systemError自动恢复**

状态恢复独立于失败任务；安全核验同线程、无活动/队列/审批后原生恢复，记录补偿义务并核对真实状态。

历史来源记录：2837, 2843, 2853, 2860。实施/验证状态以 JSON 清单为准。

- REC-01.1：持续客户端持有场景也验证恢复
- REC-01.2：archive后断连/重启须恢复active且保留历史和项目
- REC-01.3：换绑/新输入/未知提交/其他活跃轮次不恢复或重跑

**REC-02 · 容量恢复**

仅原生确认容量失败可有界空输入续接；认证/限额/安全拒绝不可当容量重跑，预算按链独立。

历史来源记录：2580, 2583, 2600, 2608。实施/验证状态以 JSON 清单为准。

- REC-02.1：旧链已结束不堵新失败但未知证据保留
- REC-02.2：队列/人工输入优先，恢复前最后校验
- REC-02.3：启动收尾只读不重放历史accepted为新运行卡

### delivery · 进展和结果交付

共享层保存按轮/分段/页的投递状态，渠道确认业务回执，客户端显示需另验。

**DEL-01 · 执行、送达和显示独立**

原生任务完成、卡片API业务成功、客户端正文显示是三个事实，不用互相替代。

历史来源记录：1331, 1334, 1383, 1391。实施/验证状态以 JSON 清单为准。

- DEL-01.1：HTTP200空对象/业务错误不是成功
- DEL-01.2：投递失败不改Codex终态
- DEL-01.3：状态报告区分已完成/未送达/未实际显示验收
- DEL-01.4：公开命令进展不泄露带引号环境变量、JSON 字段、独立 argv、URL 用户信息或 Bearer 凭据；普通命令仍有摘要。
- DEL-01.5：获取 token 失败且未发出任何创建/投递请求时，记录明确未发送并允许用原逻辑实例恢复；如果原先已有 delivery-unconfirmed，新的准备失败不能削弱该未知事实或免除显式重投确认。
- DEL-01.6：飞书 callback 仅替换本次原卡；其他兄弟卡使用精确 messageId patch；响应已经返回后的继承异步上下文不能吞掉迟到更新。

**DEL-02 · 单卡分阶段持久化**

创建/投递/首帧/更新/结束各自记录稳定实例与回执；明确拒绝可恢复原实例，未知不盲目重建。

**DEL-03 · 不追加文本兜底**

支持流式卡的渠道失败后只受控更新原卡，不能追加普通进展、替代答案卡；纯文本渠道保留本来能力。

**DEL-04 · 历史不当新任务**

持久化历史边界和当前轮证据限制恢复；未见过ID不等新完成，旧acceptance不等新开始。

- DEL-04.3：精确已跟踪未送达终态保留独立恢复记录

**DEL-05 · 分段而非任务完成**

answer/steer原生确认后展示切段；queue实际执行才新卡，旧卡留真实小结不称任务结束。

- DEL-05.2：小结失败不妨碍新段且独立保存
- DEL-05.3：分段和重启不丢参与者/原turn身份

**DEL-06 · 最终参与者原生提醒**

按turn与来源对话保存已确认参与者，顺序去重；尽量最终正文+原生@同卡，进度不反复提醒。
