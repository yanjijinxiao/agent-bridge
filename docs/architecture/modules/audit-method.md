# 四层审查与证据维护

用户要求依次看整体架构、各模块按功能意图的实现/异常/遗漏、各文件及底层函数，第四层覆盖静态文件和配置。不能把“已有测试通过”当成架构完整或没有隐藏问题，也不能为变绿而改掉真实需求。

公开历史提炼为 gateway-requirements.json：每项保留来源、契约、具体反例/正常 case、精确测试名称及源码散列。gateway-implementation-map 定位事实源和实际入口。模块说明解释状态、跨模块等待、失败归属和限制，注释说明为什么保留边界，不逐行翻译赋值。

read-ledger 记录具体版本和行范围。对后续改动，逐行相同范围可以继承已读版本；改变范围必须重新核对调用者、被调用者和持久记录，不能直接给整个新文件换 hash 冒充读过。非文本制品另记视觉/结构检查，不把二进制行数当源码。

确认缺陷需要真实入口、可隔离失败证据、正常对照，再修主路径并加必要 case。夹具错误和产品错误分开，保留第一次失败，不通过删除失败或把 unknown 改成 success 获得绿灯。默认跳过的浏览器父测试与显式 Chrome 运行分别记录。

check-audit-evidence 是只读证据工具，只检查映射、hash、范围和通过记录，既不执行产品功能，也不参与运行/发布门禁。完整阅读、精选函数合同、有限反例与真实设备验收是不同证据。审查工作可以结束一轮；没有数学意义的“以后不会再有 bug”，未验证供应商/设备条件必须如实列出。
