# Q124 回答通道与冷恢复批量读取的隔离

## 现场与边界

Q124 生产补查：问题 journal 为 pending，交互监督器对应 thread subscribed=false；Connector 固定原因诊断每约30秒产生 observer-suspended，并更换本机控制连接。另一个 notLoaded 会话原生路径约289MB，fs/readFile返回base64可能超过256MiB relay预算；现有128MiB检查在收完整响应后才执行。fs/getMetadata原生DTO没有size，不能假造可用的原生size接口。
拟修正职责：冷恢复整文件读取借用同一独立 App Server 的专用只读连接，不与任务、审批和问题通知共用。只读连接只准initialize/initialized/fs/readFile，异常和关闭只影响该连接，不创建另一个执行核心。确定为本机daemon-proxy时可以对原生返回路径做本机只读大小预检，用于拒绝既有128MiB预算之外的读取；不据此恢复权限，不读取同名远端文件。远端无本地路径旁路，仍通过同一原生服务的只读客户端。保留原最新权限投影、owner-race、绑定写前检查和失效不提交语义。
私有stdio不是共享核心：不能为隔离读取启动新的执行器。保留其原生读路径并明确此分支的既有预算限制，不宣称本次证明其大响应隔离。父Runner关闭必须关闭所有本次临时只读relay，不停止核心。
新增组合：另一个冷会话读失败/超大，与当前待答问题并行；问题原卡仍可答，显式答案一次steer并有原生确认；本机超限不发fs/readFile；远端同名本地文件不作为权限/大小依据；临时reader不得执行控制；父关闭释放reader；真实Native冷恢复的最新权限、进一步收紧和owner-race保持。


## 四层实施检查

1. 架构：同一原生核心、同一原生文件权威，仅拆分控制和大响应读取连接；不新增执行器，不缓存或另存权限，不借未知恢复扩大授权。
2. 模块：临时只读客户端失败和关闭不能触发主控制连接 failTransport。只有确认本机来源才做本机大小拒绝；远端仍读原生路径。保留原 128 MiB 解码预算，不把本次措施说成支持任意大来源的冷恢复。
3. 函数/代码：逐行检查 resumeThread → readPermissionFile → reader.ensureConnected/request/finally.close，父 close 与临时 reader 的生命周期，以及 send/handleServerRequest 的只读限制。观察原卡 Controller.pending/ask/release/unavailableAnswer，区分持久待答、内存连接和原生接受三类事实。
4. 静态/文档：核心/Connector 共用一个实现，新增构造标记不进入 Peer 协议；日志沿用 major=1，输出固定事件/原因及不透明身份，不输出文件、问题、答案正文。同步模块、功能 case、函数记录、教程和版本号。

## 复现与测试结果

在隔离的 bd36b0b 源码运行 10 项新场景：9 失败、1 保护对照通过。修改后最终针对性组合 93/93 通过，类型检查通过；真实 0.167.2 临时核心的冷恢复与相邻集成 22/22 通过。完整回归第一轮 3915 项（3814 通过、101 条件跳过），随后补充的精确恢复提示另经针对性验证；最终制品再跑全量，不混称该首轮已覆盖后来追加的断言。

跨线程故障使用生产 Runner/Controller、隔离 JSONL 传输进程和原生协议夹具：冷会话批量读取时断开其传输模拟大响应故障，活动问题原控制 PID 保留，原卡仍答，一次显式答案产生一次 steer 并经夹具确认。这不是用户钉钉实际回答验收。大文件为测试自有稀疏文件，不读生产来源正文。只读核对生产元数据得到问题线程 active、一个旧线程 notLoaded 且来源289413029字节，与共享连接反复挂起现象对应；上线后须观察实际订阅持续就绪，再报告生产恢复。

私有 stdio 大文件隔离、超过权限恢复预算的完整冷恢复仍不在本次完成范围；不得以跳过大文件读取声称这些功能已全面修复。
