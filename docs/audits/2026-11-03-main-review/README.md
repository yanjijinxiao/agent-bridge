## 确认的运行缺陷

### F1 · P1 · 新线程持久回执失败后，peer 仍提交原生输入（新增）

- 位置：`src/peer/execution-service.ts:316`、`:341`；调用方 `src/codex/app-server-runner.ts`、`src/bridge/turn-submission.ts`。
- 意图：新建原生 thread 后，Gateway 必须成功保存 thread 身份，才能继续 turn/start，确保崩溃后能够按原身份核对输入。
- 触发：通过 peer 直接 run 创建新 thread，Gateway 的 onThreadCreated 持久化回调失败。
- 实际：通用 event 包装器吞掉回调异常，原生 runner 继续 turn/start。测试实际执行 AppServerCodexRunner 与 JSONL 原生协议夹具，原生提交次数为 1，预期为 0。
- 影响：设备侧保存了 thread ID，但 Gateway 的持久记录可能缺少它，产生任务已启动、原始身份未可靠交接的窗口。不是所有创建入口都受影响；独立 createThread 管理入口不能直接套用此结论。
- 修复方向：区分必须成功的持久交接回调与尽力投递的进展通知，前者失败必须在原生输入提交前传播；保留设备侧已创建身份，不重发未知输入。
- 对应要求：IN-02、PEER-01；用例 MR-F1。

### F2 · 不计入运行缺陷 · 仅直接注入 exec 配置的独立审批观察不一致

- 位置：`src/server/account-manager.ts:2171`，对照 `:2131` 起的 threadSubscriptions。
- 意图：跟随和审批能力应按所选执行主机判断。Gateway 本地使用 exec，不应禁止远端 App Server 的原生交互。
- 测试触发：绕过配置加载，直接通过 AccountManager.configProvider 注入 exec，再绑定具备 App Server 能力的 peer。
- 实际：普通跟随订阅已支持 peer，但 ensureNativeRequestMonitor 在检查远端绑定之前直接返回，独立交互观察器未建立。
- 最后核对入口发现：`src/state/config.ts:89`、`:120` 的 loadConfig/saveConfig 均统一为 app-server；实际服务启动及 AccountManager 默认配置源使用 loadConfig。因此普通配置文件和生产启动路径不能触发这个反例，不可据此宣称当前线上审批链路有此缺陷。
- 保留原因：类型、旧条件与部分新增测试仍在支持注入 exec，暴露了兼容代码与单一 App Server 架构意图不一致。后续应清理失效分支/类型或明确内部注入合同，不能恢复已淘汰的业务执行分支。
- 对应要求：NATIVE-03、INT-02、INT-03、PEER-01；用例 MR-F2。保留原失败反例及实际配置迁移正常对照，状态为 injection-only，不作为 P1 或待上线阻断项。

### F3 · P1 · 接收连接 error 被当作停止跟随（既有，截图一）

- 位置：`src/server/account-manager.ts:2134`–`:2136`；`src/server/thread-event-hub.ts:263`–`:285`；DingTalk 连接诊断可将仍在监测的账号设为 error。
- 意图：短暂重连不等于解绑；任务、观察游标和原卡应保留。该意图已写在代码注释中。
- 实际：订阅只接受 running/starting。error 导致订阅消失，Hub 对原卡发送“已停止跟随此会话；任务继续运行”，并清除游标状态；会话绑定本身没有改变。
- 复现：实际 AccountManager + ThreadEventHub + 渠道夹具；starting 正常对照不收尾，error 情况错误收尾一次。
- 修复方向：将账号生命周期（停止、删除、禁用、替换）与入站连接健康分开。网络异常保留订阅及卡片身份；用户显式解绑/停用仍须正常退出。
- 对应要求：CHAN-04、DEL-08；用例 MR-F3。f108f81 与 3d5bff7 均有此逻辑，不归因于新增 Connector。

### F4 · P2 · 共享编辑器迟到的保存响应清掉后续编辑状态（新增）

- 位置：`src/peer/workspace-page.ts:23`，关联 `:21`、`:27`。
- 触发：保存第一版文字，响应回来前继续输入第二版文字。
- 实际：第一版写入的响应无条件设置 dirty=false、禁用保存并显示已保存。第二版仍在文本框里，但离开页面不再受未保存提示保护。
- 复现：执行生产 workspacePage 生成的实际内嵌脚本，以 DOM/fetch 替身控制响应顺序；正常保存通过，延迟响应组合失败。
- 修复方向：保存请求捕获路径、文本、编辑代次及请求身份；只有当前编辑状态仍与已确认内容相同才清脏。保留新修改，处理保存期间切文件及连续保存顺序。
- 对应要求：WEB-01、PEER-04；用例 MR-F4。这是新共享文本编辑器，不能说原 code-server 编辑器也存在同一缺陷。

### F5 · P1 · 旧回执观察超时丢弃已成功读取的当前进展（既有，截图二）

- 位置：`src/server/thread-event-hub.ts:313`–`:320`；`src/server/account-manager.ts:394`、`:1793` 起；`src/bridge/native-input-recovery.ts`。
- 意图：在执行最终结果副作用之前核对输入接受状态，同时持续显示当前原生任务的真实进展。
- 实际：快照读取成功后，先 await 旧回执核对；任意核对失败都会跳过整个快照合并，进入 failSync，连已经取得的活动状态与进展也被丢弃。
- 复现：实际 ThreadEventHub，原线程/活动轮次快照含新进展；仅使旧回执观察报超时。正常对照显示新进展，超时组合持续保留占位文字及待确认状态。
- 生产只读核对：该会话存在一条符合当前精确来源筛选规则的旧未确认输入；日志反复出现原生快照恢复、回执观察超时及重新读取链路。其他不满足来源条件的历史记录未计入。
- 修复方向：将只读运行状态/进展更新与旧输入接受核对隔离；最终结果动作和投递仍保留必要的身份及接受证据检查。对恢复读操作使用独立、有限的重试与预算，不能通过忽略未知回执或重发用户输入来“修复”。
- 对应要求：IN-02、DEL-08、REL-01；用例 MR-F5。f108f81 与 3d5bff7 均存在。
