# 原生接收与Gateway回执之间的真实崩溃恢复

用户优先要求修复真实崩溃恢复。本轮先记录职责和验收条件，再以独立原生核心与被SIGKILL的临时Gateway进程复现，不终止真实用户任务。

## 当前缺口

TurnSubmission先落盘submitting并把稳定clientUserMessageId交给原生服务；原生接收后才写accepted。进程在这两次写之间退出，ForwardingInbox会保留未确认并禁止重发，但普通输入缺少按原身份只读核对并恢复accepted的路径。新建线程的ID此前只随绑定保存，来源journal还缺提交前的线程ID更新。

## 设计约束

1. 原生线程/输入是执行事实源；Gateway只从原host/thread的公开原生用户消息中精确匹配clientUserMessageId。正文相同、未找到、读取失败、分页不完整或多轮同ID都不能授权重发或猜测接收。
2. 新建线程回调先把threadId写回来源日志，再允许原生turn/start。恢复没有足够持久身份的旧记录时保留未知，不扫别的主机或会话猜测。
3. 来源日志的恢复更新必须核对原版本、非当前活交接及精确session/host/thread；落盘成功才通知inbox清理正文。停止或替换的账号不能由迟到读取继续写旧journal。
4. 原生读取不占提交队列或重启交接门禁。独立恢复和跟随快照共用同一接受事实更新，结果投递前先核对输入来源，避免先完成投递却永久跳过附件/记忆动作。
5. 重启只重连原核心、观察原轮次，不再执行run、steer、queue/add或合成审批答案。当前绑定决定投递；恢复旧接收事实不把结果改投新绑定。

## 需要直接验证

- 使用已安装原生二进制、临时Home和本机假模型；Gateway为真实独立子进程。原生接收回调进入accepted append之前SIGKILL，磁盘只有submitting，核心仍运行且用户输入仅一次。
- 已绑定线程与首次新建线程都能在新Gateway进程找回相同thread/turn/client ID；再次重启保持去重，最终原答复及允许的结果动作一次完成。
- 未找到、相同正文不同ID、重复client ID、分页故障、落盘失败及停止/换绑的迟到读分别保留原边界。
- 保存提交标记失败仍零原生输入；accepted已经落盘的正常路径保持；恢复只读不长期挡后续输入或Gateway重启。

SIGKILL验证的是进程骤停，不代表主机断电后的磁盘硬件保证。真实供应商和手机显示另验。复现、修复与实际运行结果完成后更新本页和IN-02.2等case。

## 实际失败与修复

第一轮真实反例：原生接收后、Gateway写accepted之前SIGKILL。重启后journal仍为submitting，原核心PID和活动turn未变，但10秒内没有恢复接收事实；旧实现失败在等待accepted的断言。日志为本机临时证据native-crash-before.log。此前只证明“不重发”不足以证明“可以恢复”。

第一版修复通过已有线程与新建线程的运行中恢复，又在“新线程、任务离线完成”失败：accepted恢复成功，12秒内最终结果仍未投递。原因是Hub尚未记录该turn，新进程把已完成turn纳入历史baseline。这是实际第二个实现缺口，不是把等待延长即可修复。

最终实现：

- TurnSubmission持久标记普通原生输入；新线程回调先把原thread ID写入来源日志，再允许turn/start。
- AccountManager按原account/host/thread合并只读核对，稳定clientUserMessageId必须在完整分页中唯一对应一个turn。默认3秒、20页×100条的观察预算；后续冷却重试。读不到、分页失败/重复、超预算或跨turn重名都保留未知。
- 旧版没有输入类型字段的记录，只有保存的普通IM来源能补足分类；queue、控制、卡片操作不由此路径恢复。没有原thread ID的旧记录仍保留未知。
- recoverAccepted对原journal版本与当前交接状态作比较，落盘后才清理inbox。退休账号、配置切换和发布期间的迟到读不能写入旧来源。读取不持有提交/重启交接锁。
- accepted同时持久保存recoveredNativeInput投递义务。Hub在结果处理前先核对输入事实；仅精确绑定、会话、主机、群对应的恢复义务可越过历史baseline。其他历史不重放，旧结果不覆盖新的活动轮。
- Hub保存最终投递确认后，journal将该恢复义务置为handled；两次保存之间再次崩溃，下一进程根据Hub的原投递事实补结算，不再次投递。附件/记忆动作仍共用TurnResultActions原有去重日志。

## 测试与边界

新增6种真实原生核心/Gateway子进程场景：已有/新线程×执行中/离线完成四种；恢复accepted写入前再次SIGKILL；新线程离线完成、恢复accepted已fsync而Hub未接管时再次SIGKILL。每种核对core PID不变、相同client/thread/turn、真实历史输入一次、原结果一次、记忆动作一次、第三次连接不重复、inbox最终清空。原生二进制为本机0.166.0，模型是本机受控HTTP服务，IM发送端口为确认回执替身；没有触碰真实用户任务。

新增13个边界检查：完整分页/精确身份、相同正文、缺少身份、重复ID、后页失败/循环/超预算、超时迟到、持久恢复及拒绝重认领、活交接/旧版本/错误scope、fsync失败、持久投递义务、新线程身份落盘失败零输入、账号退休/只读不挡发布、旧普通来源与控制区别、换绑仍核对原目标、旧结果不覆盖新进展/无关历史不重放。其中有些测试包含多种反例，不把断言数量当作额外case计数。

完整回归首次运行2717通过、1失败、1跳过；失败为原生started后过早读取尚未落盘的首条历史。夹具增加“本机模型确已收到原输入”的同步条件，保留原活动turn及次数断言。最终完整回归2718通过、1项Windows专用跳过；六个真实崩溃场景与十三个边界均实际执行，无默认跳过。

首次扩展测试曾错误依赖未订阅的新线程广播，改为直接查询原核心完成状态；两个边界夹具曾使用非法release ID和旧状态库快照，改为合法UUID与唯一live owner。失败记录保留，不混同以上两个产品缺口。没有放宽生产恢复条件或延长失败断言掩盖缺陷。

最终全量运行和发布结果见下方完成记录。IN-02.2继续partial：不覆盖任意CPU指令间隙、主机断电、真实SSH掉线/供应商回执/手机呈现；原生队列与workflow未知交接仍由各自case验证。历史缺原thread ID、分页超预算或原生未暴露client ID的记录不会猜测重发。此轮没有完成全仓重新通读，只继承逐字未变的已读范围，逐行核对本次变化与直接调用链。

## 四层核对

1. 架构：原生唯一执行事实源；Gateway来源日志与结果投递日志分别持久，恢复没有第二条执行链，不持有整个任务锁。
2. 模块：普通提交→新线程身份→原生接收→恢复确认→结果动作→Hub最终投递→结算；核对账号退休、当前绑定改变及新轮次并存。
3. 文件/函数：native-input-recovery、inbound-receipts、turn-submission、forwarding-inbox、AccountManager与Hub的差异、调用者和测试夹具；精选函数合同记录意图、范围及源码散列。
4. 静态/配置：沿用标准App Server历史分页，不新增执行入口/端口/权限开关；旧journal版本增加可选事实字段，回滚仍保留accepted不重发；测试仅显式原生环境变量启用，私有临时状态与生产分开。当前入口、模块说明、人读功能与需求JSON同步。
