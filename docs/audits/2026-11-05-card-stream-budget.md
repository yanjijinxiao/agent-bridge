# 钉钉长任务卡停在旧帧的排查

## 实际证据与结论边界

用户手机 19:10 截图中，18:29 创建的旧卡仍显示“进行中 · 14秒”，19:07 的续卡显示约40分钟。对应原生任务没有中断。日志显示旧卡在 19:07:45 已收到最终流式帧和 flowStatus=3 的成功回执；通过 dws 只读查询原群的这两条消息，旧卡文本已是“已转入后续卡片”和完整阶段小结，续卡文本随后为“已完成”。这说明服务端消息正确，不能由此推断手机渲染已恢复，更不能归因于后来 19:18 的上线重启。

旧卡的377次进行中更新，309次记录的正文超过1024字节，119次超过3072字节，最大3922字节。第一次超过1024字节发生在18:35:54，比截图停住的“14秒”晚。因此超预算是已确认的接口适配缺口，尚不能认定是该截图停帧的唯一根因。反复全量替换流式Markdown中的阶段正文也扩大了客户端增量解析的依赖面。

官方[AI卡片流式更新](https://open.dingtalk.com/document/development/api-streamingupdate.md)要求完整Markdown，建议单次内容不超过1K、总大小不超过3K；isFull 表示覆盖，isFinalize 表示最后一帧。原代码将整个卡片的6000字节分页预算当作流式内容预算使用，两者不同。字段、文档与请求记录于本轮直接核对；没有从“API已接收”推断“屏幕已显示”。

## 修复与四层范围

1. 架构：阶段成果、滚动活动、原生执行状态、卡片持久化及渠道回执仍各守原边界。可信顶部状态只用短流式帧；其余完整正文及原停止复制框/IDE链接通过普通卡片快照更新。原模板与顺序保留，顶部状态使用原生加载反馈；不缩减成果、不按工具活动频繁新建卡片。
2. 模块：检查共享渲染器→ChannelTurnTextStream→ChannelTurnPresentation→钉钉HTTPS/SDK的创建、更新、切段、重连、等待和终态路径。静态快照确认后才更新缓存，失败不会凭状态流成功而宣称正文已送达；心跳不重写未变正文。终态不先重进输入态或清空最后可读正文。
3. 函数：逐行核对 renderTurnProgressLayout、activeDingTalkLayout、initialDingTalkCardData、两种 updateWithRetry 及 updateCardState、状态参数构造、原 stageSummary/closeSegment。status 是可信渲染字段，仅在完整段落边界剥离；旧调用缺失时保留全部正文。检查UTF-8预算、最终短帧、已确认旧卡句柄、序列化更新与失败缓存。
4. 静态/配置：检查既有模板 order、contentKey/staticMsgContent、复制围栏、IDE装饰器和6000字节分页；不增加模板字段、部署授权或持久化布局字段。更新状态设计、阶段架构、渠道模块、需求 DEL-09.5、函数职责及架构索引。
