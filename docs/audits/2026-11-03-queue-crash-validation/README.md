# 原生队列交接和并发的追加验证

基线 c9662db。本次继续 remaining-work 的 CTRL-02.1、CTRL-03.1/3/5；是关键缺测组合的增量验证，不是又一次全库逐行检查。生产头头和用户任务不参与故障注入。

## 发现与修复

1. queue/add 原生已接收、本地接收回执尚未落盘时骤停，恢复能送回结果，却没有清理原始 IM 的 forwarding inbox。新增按原账号、消息、操作者、会话、主机和线程精确匹配的队列来源恢复，并比较当前回执版本；活交接、普通输入和冲突来源不能改写。先保存接收证据再清理 inbox，结果义务仍只归原队列。
2. Hub 先看到完成结果、队列监控尚未恢复 turn ID 时，附件和记忆动作被当成没有 Gateway 来源而漏掉。现在先只读核对该账号、会话、主机、线程的队列来源；读取失败暂缓，退休账号或错轮次不执行动作，原动作日志去重。
3. 原生分页历史与运行态读取交错，会把运行中的队列轮次提前展示为中断。Hub 的一致性检查提前到任何卡片结算之前；原生适配器在读历史后复核运行态，并拒绝明确 completedAt=null 的终态标签。较旧的缺失结束回执不会遮蔽新完成结果；旧协议省略字段保持兼容。真正完成和主动停止在真实 0.166.0 核心中均有结束时间，已对照核验。
4. 原生任务完成但 Hub 尚未确认送达时，队列仍会记为 delivered。现在成功、失败、中断共享原 Hub 投递日志，并向队列返回实际投递回执。未送达仅重读、投递原轮次结果，不重新 queue/add、start 或 steer。

## 四层核对

- 架构：Codex 负责执行和原生队列；来源日志负责 IM 交接；Hub/动作日志负责展示和结果；三种回执不能相互代替。Gateway/Connector 故障不结束独立执行器。
- 模块与遗漏场景：加入来源 CAS、同源只读恢复、迟到结果动作、active/终态冲突、显式缺结束回执、失败与中断投递、正常待项、账号退休与错 turn。
- 文件与函数：修改的六个实现文件记录实际阅读范围；function-delta-review 列出选定函数 AST 是否改变，function-contracts 更新职责、边界与 case。未变函数沿用既有审查，不声称本轮重新阅读。
- 静态/配置：功能清单、模块文档、剩余清单与 case 汇总同步；检查构建制品及三端测试服务入口。配置身份与凭据沿用测试环境，没有改生产配置、权限策略或原生执行入口。

## 验证设计与失败记录

新增 31 项测试。六种真实 SIGKILL 使用独立原生核心与实际 AccountManager/Bridge/队列/inbox/Hub 子进程：接收回执 rename 前后、pending/running/离线完成、恢复再次退出。原生执行真实，模型是本机受控 HTTP 服务、IM 是 TEXT 传输替身。断言核心 PID 不变、原输入一次、最终答复/记忆一次、inbox 清空、第二次重启不重复投递。三种并发 append 在两客户端各写两项后，验证正常、写入端断连、全部客户端断连的原生 FIFO 消费。

第一次六种执行恢复通过后，补查 inbox 才暴露遗留来源。继续联合附件/记忆与投递日志断言，又暴露来源恢复先后及提前终态；某次完整回归在 after/pending 真实复现“任务已停止”却无原结果，未记为通过。重复通过本身没有用来否认该失败。新结束回执反例和六种骤停共 22 项已通过；最终完整根回归 3064 项，3063 通过、1 项 Windows 专用跳过，类型检查和构建通过。探探及 Linux/Mac Connector 已切换 queue-crash-verified 测试制品；执行中实际 SIGKILL 两个转发进程，同一原生轮次完成，文件开始/结束各一行，IM 文件与答复各一条，本次 inbox 来源清除。Mac 目录读取正常，原 Linux 绑定已恢复。详见 validation-summary.json；生产头头未切换。

迭代期间完整回归还发现一处旧私有测试夹具没有传入新的投递回调，已补齐。叠加额外原生压力批次时发生一次 5 秒 initialize 超时；未放宽产品超时，最终完整回归独立运行，历史失败保留在证据摘要，不能称该超时原因已被产品修复。
